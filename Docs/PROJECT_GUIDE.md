# SIGNAL RUSH 프로젝트 가이드

이 문서는 48시간 게임잼 동안 코드와 게임 디자인 결정을 빠르게 공유하기 위한 작업 기준이다. 기능의 정본은 `SIGNAL_RUSH_GDD_v0.1.md`이며, 이 문서는 GDD를 구현할 때 필요한 엔지니어링 판단만 보충한다.

## 1. 기준과 우선순위

충돌이 생기면 아래 순서로 판단한다.

1. GDD v0.1의 기능 잠금(F1~F6), 컷 리스트, 불변 조건
2. 이 문서에 기록된 팀 결정
3. 현재 씬·프리팹의 직렬화 계약
4. 현재 코드의 동작

현재 동작이 GDD와 다르면 현재 동작을 새 설계로 간주하지 않는다. 차이를 먼저 기록하고, 기능 추가와 리팩터링을 섞지 않는다.

프로젝트 기준은 Unity `6000.5.9f1`, Windows standalone, 키보드 입력, URP 2D다. GDD 원본은 2026-08-20에 전달된 `SIGNAL_RUSH_GDD_v0.1.md`이며 원본에 참조된 `figures/`는 전달되지 않았다.

## 2. 주석 가이드

주석은 한국어로 쓰며 코드가 표현하지 못하는 이유·제약·외부 오브젝트와의 계약만 설명한다. 코드와 같은 말을 반복하는 주석은 쓰지 않는다. 이 기준은 [Google Engineering Practices](https://google.github.io/eng-practices/review/reviewer/looking-for.html)의 “무엇보다 왜” 원칙과 [C# 주석 문서](https://learn.microsoft.com/dotnet/csharp/language-reference/tokens/comments)를 따른다.

- 남긴다: 씬/프리팹 배치 전제, GDD 불변 조건, Unity 시간축·생명주기 선택 이유, 의도적인 게임잼 단순화
- 남기지 않는다: 메서드 이름을 한국어로 반복한 설명, 명백한 분기·대입 설명, 모든 필드의 형식적인 XML 문서
- 임시 결합은 현재 한계와 제거 시점을 함께 쓴다.
- 코드가 바뀌면 관련 주석도 같은 변경에서 고친다. 맞지 않는 주석은 없는 주석보다 위험하다.
- Inspector에서 값을 조정하는 사람이 알아야 할 범위·단위는 코드 주석보다 `[Tooltip]`, `[Min]`, `[Range]`를 우선한다.

예시:

```csharp
// 일반 대기는 timeScale 0에서 끝나지 않으므로 실제 시간 기준으로 히트스톱을 해제한다.
yield return new WaitForSecondsRealtime(hitStopDuration);
```

## 3. 코딩 컨벤션

GDD §10을 그대로 따른다.

- 클래스, 메서드, public 프로퍼티: `PascalCase`
- private 필드: `_camelCase`; 지역 변수: `camelCase`
- Inspector 노출: `[SerializeField] private`; public 필드 금지
- 한 파일에 한 클래스
- Unity 이벤트 함수는 클래스 위쪽에 생명주기 순서대로 배치
- `Update`/`FixedUpdate`에서 `GetComponent`, `Find` 금지; `Awake`에서 캐싱
- GDD의 `TUNE-*` 값은 직렬화 필드 또는 이름 있는 상수로 둔다.

이름만 맞추는 대규모 변경은 게임잼 중 하지 않는다. 직렬화 필드 이름을 바꿔야 한다면 `[FormerlySerializedAs]`로 기존 씬·프리팹 값을 보존한다.

## 4. SOLID 적용선

SOLID는 클래스 수를 늘리는 목표가 아니라 변경 위험을 줄이는 질문으로만 사용한다.

- SRP: 서로 다른 이유로 자주 바뀌는 책임이 실제로 확인될 때만 분리한다. 카메라 구성은 씬으로 옮겼지만, 이동·점프·공격은 게임잼 동안 `Player`에 함께 둔다.
- OCP: 장애물·청크 종류가 데이터와 프리팹 배열로 늘어나는 동안 새 인터페이스나 팩토리를 만들지 않는다.
- LSP/ISP: 구현체가 하나뿐인 인터페이스를 만들지 않는다.
- DIP: Unity 컴포넌트 참조는 Inspector 직렬화와 `GetComponent` 캐싱을 사용한다. 서비스 컨테이너나 로케이터를 도입하지 않는다.

분리 기준은 다음 중 하나가 실제로 생겼을 때다.

- 같은 클래스가 서로 무관한 두 기능 때문에 반복해서 수정된다.
- 테스트 하나를 위해 씬 전체를 구성해야 한다.
- 한 책임의 상태 전이가 다른 책임의 상태를 자주 깨뜨린다.

## 5. 현재 구현과 GDD의 차이

| 영역 | 현재 구현 | GDD v0.1 | 판단 |
|---|---|---|---|
| F1 이동 | 자동 우측 이동만 존재 | 좌/우 미세 조정 포함 | 기능 차이. 리팩터링으로 구현하지 않음 |
| F2 점프 | 누르는 동안 힘을 더하는 모델 | T1/T2 감쇠 중력 모델 | 기능 차이. 현재 수직 슬라이스를 먼저 보존 |
| F3 공격 | 공격 재입력 시 판정 시간을 다시 시작 | 공격 중 재입력 무시 | 기능 차이 |
| F3 파괴 | 장애물 전체를 밀어낸 뒤 지연 삭제 | 파편 플립북 | 임시 시각 연출로 유지 |
| F4 패링 | 없음 | 총알 존재 중 공격 시 성립 | 미구현 기능 |
| F5 콤보 | 값과 속도식은 있으나 성공 시 증가하지 않음 | 파괴·패링 시 증가, 피격 시 초기화 | 미구현 기능 |
| 체력/런 종료 | 5초 이상 공중이면 즉시 게임 오버 | 체력 0 또는 목표 도달 | 프로토타입 임시 규칙 |
| F6 생성 | 각 슬롯마다 장애물/빈칸을 독립 선택 | 청크별 슬롯 세트 0/1/2 선택 | 기능 차이 |
| 청크 정리 | 청크만 카메라 뒤에서 삭제 | 소속 스나이퍼 생명주기까지 보장 | 장애물·향후 스나이퍼 정리 계약 필요 |
| 카메라 | 씬에 Cinemachine Brain/Follow 카메라 저장 | 씬 구성 + Pixel Perfect | 책임 분리 완료. Pixel Perfect는 별도 기능 작업 |
| 튜닝 | 콤보 증가율을 직렬화 필드로 관리 | `TUNE-C2`로 관리 | 구조 일치, 값은 플레이 테스트 대상 |
| 컨벤션 | 직렬화 private 필드와 `_camelCase` 사용 | `[SerializeField] private`, `_camelCase` | 기존 값은 `FormerlySerializedAs`로 보존 |

## 6. 테스트 원칙

현재 테스트는 구현 세부보다 Unity 에셋 계약을 보호한다.

- 씬에 플레이어, 플랫폼 매니저, Main Camera와 필수 직렬화 참조가 존재하는지 검사한다.
- 건물 프리팹의 시작점·끝점·장애물 슬롯과 장애물 프리팹의 물리 컴포넌트를 검사한다.
- private 메서드 호출, 프레임 타이밍, 랜덤 결과 하나를 고정하는 테스트는 쓰지 않는다.
- 순수 계산이 생기면 EditMode 단위 테스트를 추가하고, 실제 물리·코루틴 상호작용이 필요할 때만 PlayMode 테스트를 추가한다.
- PlayMode 스모크 테스트는 SampleScene을 실제 실행해 런타임 오브젝트 중복과 예외만 확인한다.

## 7. 변경 완료 기준

1. GDD의 어떤 ID를 보존하거나 맞추는지 변경 설명에 적는다.
2. 새 기능을 리팩터링에 섞지 않는다.
3. 관련 EditMode 테스트와 C# 빌드가 통과한다.
4. 씬·프리팹 직렬화 값이 유지된다.
5. 팀원이 설명 없이 diff를 읽을 수 있을 만큼 변경을 작게 유지한다.
